# Check status, evaluation, and recovery

Use this short guide when a first run appears stuck, finishes without a clear result, or its evaluation fails. It covers the status and evaluation steps linked from the English quickstart. The broader recovery procedures, including detailed CLI and host-specific cases, are currently documented in Korean: [status guide](/docs/status-guide/), [recovery guide](/docs/recovery-detail/), and [evaluation guide](/docs/evaluation-evolution-detail/).

For installation, MCP connection, authentication, and update problems, see the English [AI troubleshooting guide](/docs/en/ai-troubleshooting/). The checks below are a short first branch, not a translation of that full guide.

## Installation or MCP connection: first checks

First identify the affected machine, user, host, project folder, and installation. A host plugin and its MCP server may be a different installation from a standalone CLI in your terminal. If that shell has the CLI, check `command -v ouroboros`, `ouroboros --version`, and `ouroboros --help` there; this identifies that shell's CLI, not necessarily the server used by the host. If the command is missing, inspect the host's plugin/server status instead of installing another CLI just to infer the host server version. Main `592c667f` and public release `0.59.9` do not establish which version your host runs.

In the original host, distinguish a disabled/missing tool from a server startup or connection error, tool discovery failure, and authentication error. Check the host's server status and the configured command or URL in place. Do not paste credentials, tokens, full environment dumps, or entire configuration files into a chat. Paths, IDs, project names, prompts, errors, and launcher arguments can also be sensitive; redact shared output. The detailed [English diagnostic guide](/docs/en/ai-troubleshooting/) covers more symptoms and command limits.

If the affected environment has the standalone CLI and supports the commands, inspect `ouroboros mcp doctor` and, for Codex `ooo auto` dispatch, `ouroboros codex doctor`. Read `--help` and each warning/error. The default `mcp doctor` checks prerequisites but does not start the server; a pass does not prove a live host connection, valid authentication, or a model call. It may still make network requests or leave local traces. The optional `ouroboros mcp doctor --probe-local-stdio` starts a temporary local child to check startup and tool discovery; it does not test the host's configured launcher or authentication, and Python-level restrictions are not OS isolation. `ouroboros codex doctor --live-mcp` starts the configured stdio server, so inspect its command and possible effects before choosing to run it; it does not test URL transport or a model call. Do not run these optional process-starting checks without first deciding that their effects are appropriate.

Treat diagnostics as observations, not authorization to rewrite host settings. Before any setup, repair, or configuration change, review the exact target and expected effect and make that change only when the user has chosen it. Then repeat the relevant check in the same host and environment. A clean CLI doctor is not confirmation that the host connection works; confirm with the host's actual tool list/connection state, and report separately if authentication or a model call remains untested. See the public [MCP doctor source at main `592c667f`](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/mcp_doctor.py), [Codex doctor source](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/codex.py), and [setup source](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands/setup.py).

## First, identify what actually started {#status}

Keep the original start response and use the ID from the correct field. An ID prefix is only a hint; the returned field and tool description determine its type. Do not substitute a job ID for a session ID, invent an ID, or treat a missing result as proof that nothing is running.

| ID returned by the start operation | What to check |
| --- | --- |
| `job_…` | In the host, use the matching `ouroboros_job_status` or `ouroboros_job_wait`; after a terminal status, read `ouroboros_job_result`. With the standalone CLI, use `ouroboros job status`, `ouroboros job wait`, and `ouroboros job result` with that same ID. |
| `orch_…` session ID | Standalone CLI: `ouroboros status run --session-id SESSION_ID`. In a host, use the session status tool if the connected server exposes it. |
| execution/run ID | Standalone CLI: `ouroboros status execution EXECUTION_ID --events`; `ouroboros status run EXECUTION_ID` shows the run/stage/step projection. |
| `auto_…` from `auto_session_id` | Standalone CLI: `ouroboros status auto AUTO_SESSION_ID`. |
| `exec_…` or another handle | Read the start response and find the associated `session_id`, `execution_id`, or `job_id`; then use the matching status path. |

If the response says `job_id: null` or `delegated_to_plugin`, do not guess a job ID. Check the same host's task/child-session view and the handoff response. Tool names and input fields can vary by installed server; check its current tool schema. CLI commands above are not MCP JSON arguments.

For the standalone CLI, `ouroboros status executions` lists recent executions (10 by default); add `--all` to remove that list cap. `ouroboros resume --list` lists in-flight sessions (20 by default); it is a lookup, not a resume, and it can omit sessions it cannot reconstruct. These lists cover different records. An empty list does not prove that no job exists or that restarting is safe. Status commands may read or update persisted observations, so confirm the active environment and database before querying. The source documents `resume --list` as an EventStore read-only lookup; that guarantee does not apply to every status command or to the whole environment.

## Read the result, not just the status {#evaluation}

For a background job, check the same ID again. `running` means keep observing that job; `completed` means read its result; `failed` or `cancelled` means inspect the error and any work already done. A successful status lookup only means the lookup succeeded. Even `completed` is not proof that the goal passed evaluation.

Before evaluating or retrying, confirm the actual session ID, original Seed, artifact, project/worktree path, branch, and any active evaluation or chained Ralph job. Inspect the files and test/evaluation evidence in the reported workspace. Do not start another evaluation chain while one may still be active.

Evaluation outcomes have distinct meanings:

- `approved` requires at least one executed mechanical check, all checks to pass, and no unresolved hold from an executed model stage in the documented formal evaluation pipeline.
- `rejected` means the formal gate withheld approval despite executed evidence. This can happen because a mechanical check failed, or because mechanical checks passed but model review withheld approval (for example, a semantic score gate or reward-hacking veto). Read the stage-specific reason; do not assume every rejection is a failed test. [Historical evaluation gate source](https://github.com/Q00/ouroboros/blob/722172ef096767583679d04aef5e847458fee6b2/src/ouroboros/evaluation/models.py#L550-L605).
- `unverified` means the required check evidence is missing. It is not approval, even if model feedback is positive.
- `NO CHECKS EXECUTED`, an evaluation error, or unclear coverage output is not a pass. Inspect the actual commands, exit codes, logs, and criterion-specific evidence; a field such as `executed=false` may describe parsed evidence and does not by itself prove a command never ran.

### Choose the next step from the evaluation evidence

An evaluation can run project-configured checks and model review, so it may take time, incur model costs, and execute project commands. First read the evaluation job result, stage-specific reason, and whether code changes were detected. Do not treat an error response as `rejected`, `approved`, or a completed evaluation.

- For `unverified`, inspect `.ouroboros/mechanical.toml` in the reported project root and the actual check output. Confirm that at least one suitable executable check is configured and that it ran. If checks need to be added or changed, review the exact commands, workspace, permissions, and possible file or network effects; leave the configuration change to the user's decision. `ouroboros detect` may call a model or write configuration and can overwrite an existing file with `--force`; check the installed help and existing files first. After evidence is available, request evaluation again for the same confirmed session, Seed, artifact, and absolute project path.
- For a Stage 1 mechanical rejection, read the failed command and its output. If the result says code changes were detected, fix the failure before evaluating that result again. If no code changes were detected and there is no result to evaluate, run the task first; an evaluation cannot create the missing implementation.
- For a Stage 2 model-review rejection, inspect the semantic feedback and address the identified acceptance-criteria issue in a new task/run or an explicitly chosen refinement. For a Stage 3 consensus rejection, inspect its reason and reconsider the requirements; the evaluation skill lists Interview or an unstuck discussion as possible next steps. A mechanical pass does not override a model-stage hold.

These are outcome-specific options from the evaluation skill, not automatic authorization to modify files, rerun a task, or start an evolution loop. In the cited main source and release `0.59.9`, a background evaluation with `auto_evolve` enabled attempts to enqueue a Ralph follow-up when `final_approved` is false; this includes both `rejected` and `unverified` results (no executed evidence). A Seed must be available, and the attempt can be skipped or fail, so inspect the evaluation result for a chained job ID, skip, or error before concluding that a follow-up started. A follow-up may make additional model calls and incur cost. Use `auto_evolve: false` on a new evaluation to prevent that evaluation from attempting to schedule a successor; it does not stop an existing chain. Check all existing evaluation and chained job IDs, their terminal results, and any already-running chain before choosing another action. See [`evaluation_job.py` at main `592c667f`](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools/evaluation_job.py#L250-L301) and [release `0.59.9`](https://github.com/Q00/ouroboros/blob/5f5fca90662861201ff0a26f502edd22b272c4c6/src/ouroboros/mcp/tools/evaluation_job.py#L250-L301). For user-facing guidance, also compare the [evaluation skill at main `592c667f`](https://github.com/Q00/ouroboros/blob/592c667f076c3dad7ef68d7844e91480d80135d0/skills/evaluate/SKILL.md), [Chinese quickstart](/docs/zh/quickstart/), and [formal evaluation guide based on historical `722172ef`](/docs/evaluation-evolution-detail/). The skill and historical guide may differ from release `0.59.9` and the installed host/server; inspect installed help and actual results.

If a new evaluation is appropriate, the English quickstart suggests asking the host for `ooo evaluate <actual session ID> [artifact]` and supplying the absolute project path. Replace placeholders with the real values; do not run a guessed command or evaluate the wrong workspace. Set `auto_evolve: false` when requesting evaluation only. This prevents that evaluation from scheduling a new Ralph successor; it does not cancel an evaluation or chain already started. If the response includes an evaluation job ID, follow that job to its result and check any returned chained job ID too. A start receipt is not a completed evaluation.

## If work was interrupted {#recovery}

Preserve the original response, records, Seed, and workspace. First determine whether the owner process is still running and inspect the matching session/job/execution, branch, files, and possible external effects. A connection loss does not show that the work stopped. A failed or cancelled label does not prove that file changes or external actions were rolled back.

Do not immediately rerun, resume, or cancel. `resume --list` only finds sessions; an actual resume can attach to a session or create a new attempt, and may create a branch or files. A process restart does not necessarily restore the old execution context. Terminal `failed`, `cancelled`, and `completed` sessions are not guaranteed to resume as the same attempt. Repeated runs can repeat external effects. Only consider a retry after confirming no prior worker or successor remains active and that repeated effects are safe. Consult the Korean recovery guide for the detailed state- and host-specific decision steps. Do not use a cancel or resume command unless that action is explicitly intended and the target ID and impact are confirmed.

## Source and verification scope

The English quickstart and current status/ID commands are aligned to public product main commit [`592c667f`](https://github.com/Q00/ouroboros/tree/592c667f076c3dad7ef68d7844e91480d80135d0), including its [CLI status implementation](https://github.com/Q00/ouroboros/tree/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/cli/commands) and [MCP handlers](https://github.com/Q00/ouroboros/tree/592c667f076c3dad7ef68d7844e91480d80135d0/src/ouroboros/mcp/tools). Detailed recovery and formal evaluation behavior cited by the Korean guides was examined against historical commit [`722172ef`](https://github.com/Q00/ouroboros/tree/722172ef096767583679d04aef5e847458fee6b2); do not assume those details are identical to main, release `0.59.9`, or your installed plugin/server. This document summarizes those concepts for first-run triage and is not a full translation of the Korean guides. This task did not query a user's host, database, job, or session, start a model or task, or verify real recovery across hosts and versions. Check the installed CLI help and connected server schema before relying on version-sensitive behavior. See the [version guide](/docs/version-guide/).
