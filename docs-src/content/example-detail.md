# 예제: 작은 작업 관리 CLI

!!! warning "판본과 검증 범위"
    별도 표시가 없으면 이 안내는 제품 소스 [`722172ef`](https://github.com/Q00/ouroboros/tree/722172ef096767583679d04aef5e847458fee6b2)를 기준으로 합니다. 제품 main [`592c667f`](https://github.com/Q00/ouroboros/tree/592c667f076c3dad7ef68d7844e91480d80135d0), 공개 패키지 `0.59.9`, 설치한 호스트와 MCP 서버는 각각 다른 판본일 수 있습니다. 기존 합성·대역 시험은 명시된 조건에 한정되며 실제 모델·외부 서비스·모든 호스트의 실행을 입증하지 않습니다. 현재 설치의 도움말과 [제품 문서](https://github.com/Q00/ouroboros/tree/592c667f076c3dad7ef68d7844e91480d80135d0/docs)를 대조하고 구판 동작이 같다고 가정하지 마세요.


이 예제는 문서의 사용 순서를 보여 주는 **가상 시나리오**입니다. 실제로 Ouroboros를 실행하거나 신규 사용자를 시험해 얻은 결과가 아닙니다. 명령·파일 경로·출력은 사용하는 프로젝트와 설치 환경에 맞춰 확인하세요.

## 현재 상황

처음으로 새 작업을 시작하려고 합니다. 만들 결과는 `add`로 작업을 추가하고 `list`로 확인할 수 있는 작은 CLI입니다. 이미 있는 앱에 같은 기능을 추가한다면 먼저 [기존 프로젝트 적용](/docs/existing-project-detail/)에서 저장소와 검증 명령을 고르세요.

## 입력

[첫 실행 안내](/docs/first-run-detail/)에서 설치·런타임 준비를 마치고 새 프로젝트 폴더를 만든 뒤, 아래 목표를 인터뷰에 입력합니다. 모델 호출은 비용이 들 수 있고 실행은 해당 프로젝트 파일을 변경할 수 있습니다.

```text
작업 관리 CLI를 만든다. add로 작업 이름을 추가하고 list로 저장된 작업을 보여 준다.
add "문서 읽기" 뒤 list에 "문서 읽기"가 나타나야 한다.
두 기능을 검증하는 프로젝트 테스트를 작성하고 실행한다.
```

- **호스트 플러그인:** 프로젝트 폴더를 열고 `ooo interview`에 위 목표를 전달합니다. 질문에 답한 뒤 `ooo seed`로 YAML을 만들고, 그 Seed를 지정해 `ooo run`을 요청합니다.
- **독립 CLI:** 프로젝트 폴더에서 아래 명령으로 같은 목표와 확인 조건을 전달합니다. `Start workflow now?`의 기본 응답은 Yes이므로 먼저 Seed를 읽으려면 `n`을 선택합니다. 이후 출력된 실제 Seed 파일 경로를 읽고 `ouroboros run /path/to/seed.yaml`의 예시 경로를 그 경로로 바꿉니다. 이미 Yes를 선택했다면 실행을 시도한 것이므로, 시작 전에 오류가 났는지와 기존 작업의 상태를 먼저 확인하고 중복 실행하지 않습니다.

    ```bash
    ouroboros init start '작업 관리 CLI를 만든다. add로 작업 이름을 추가하고 list로 저장된 작업을 보여 준다.
    add "문서 읽기" 뒤 list에 "문서 읽기"가 나타나야 한다.
    두 기능을 검증하는 프로젝트 테스트를 작성하고 실행한다.'
    ```

    이 입력은 목표 전달 예시이며, 인터뷰에서 생성된 Seed에 각 조건이 실제로 포함됐는지 실행 전에 확인해야 합니다.

## 예상

호스트에서는 인터뷰 완료 뒤 별도 Seed 생성 단계가 있고, CLI의 `init start`는 인터뷰 뒤 생성이 승인되고 성공하면 Seed 생성을 이어갑니다. 중단·거절·실패 시에는 Seed 파일이 있다고 가정하지 않습니다. Seed에는 `add`·`list`, 입력한 작업 이름이 목록에 표시되는 조건, 테스트 실행이 완료 조건으로 있어야 합니다. 실행 요청에서는 조회할 ID를 받을 수 있지만, 그것은 작업 접수 또는 실행 식별자이지 성공 증거가 아닙니다.

## 확인

실행 전과 실행 후를 나누어 확인합니다.

1. **실행 전 — 목표와 대상:** Seed의 목표·대상 경로·완료 조건에 `add`, `list`, 같은 이름의 재조회와 테스트가 들어 있는지 읽습니다. 빠진 조건이 있으면 실행 전에 보완합니다. 프로젝트 폴더와 기존 변경도 확인합니다. CLI에서 대상 경로가 명시되지 않으면 실행 당시 폴더가 사용될 수 있습니다. 별도 worktree를 사용하는 실행은 원본의 미커밋 변경을 포함하지 않을 수 있으며, 작업 공간 준비에는 기존 관리 경로 삭제 조건도 있습니다. [경로 선택 조건](/docs/first-run-detail/)과 [작업 공간의 기준·삭제 경계](/docs/existing-project-detail/)를 실행 전에 확인하세요.
2. **접수 후 — 같은 작업 추적:** 실제로 받은 ID를 기록하고 [진행상태 확인](/docs/progress-detail/)에서 해당 ID에 맞는 방법으로 조회합니다. ID를 받거나 조회 명령이 성공한 것만으로 작업 완료를 뜻하지 않습니다. 아직 진행 중이면 같은 작업을 계속 확인하고 중복 실행하지 않습니다.
3. **종료 후 — 결과 위치 확인:** 호스트 응답의 `worktree_path`·`worktree_branch` 또는 독립 CLI 출력의 `Task worktree`·`Task branch`가 있는지 확인합니다. 별도 worktree가 항상 생기는 것은 아닙니다. 경로가 보고되지 않으면 실행 결과와 프로젝트 경로를 확인합니다. 실제 작업 위치에서 생성된 프로젝트 문서와 설정·진입점을 읽어 실행 방법과 테스트 명령을 확인하세요. 작업 위치의 변경이 원래 브랜치에 자동 반영됐다고 가정하지 않습니다. 설명이 없으면 호스트에 파일 근거와 함께 찾아 달라고 요청할 수 있습니다.
4. **동작과 테스트 확인:** 생성된 프로그램이 안내하는 실제 호출 형식으로 작업을 추가하고 목록에서 같은 이름이 보이는지 확인한 뒤 프로젝트의 테스트를 실행합니다. 위의 `add`와 `list`는 기능 요구의 예시이며 실제 호출 형식이 아닐 수 있습니다. `add`는 데이터를 쓰므로 저장 위치와 기존 데이터를 먼저 확인하고, 지원한다면 테스트 전용 임시 저장소를 지정하세요. 테스트가 수정하는 파일도 구현에 따라 다릅니다.
5. **실패 또는 불일치:** 실패한 단계와 출력, 실제 작업 위치와 ID를 보존하고 [복구 안내](/docs/recovery-detail/)를 따릅니다. 작업이 끝났다는 상태와 요구 사항을 충족했다는 판단은 구분합니다.

**확인한 범위:** 임시 프로젝트 시험은 고정 원본 `722172ef` 자체가 아니라 그 후손인 제품 소스 [`4ff13e838bd332693c9b959fd22861dda5a1d525`](https://github.com/Q00/ouroboros/tree/4ff13e838bd332693c9b959fd22861dda5a1d525)과 별도 가상환경을 사용했습니다. 두 커밋 사이에는 provider 소스 세 파일 등의 차이가 있습니다. 독립 CLI 실행 경로와 runner에 가짜 작업자 및 사전검사 대역을 주입한 시험에서, 요구 파일을 만들고 로컬 확인 명령을 통과한 한 사례는 `run`과 별도 `status run --json`이 모두 종료 코드 0이고 상태에 `pass`를 포함했습니다. 요구 파일을 만들지 않은 다른 합성 사례는 `run` 종료 코드 1, 별도 상태 조회 종료 코드 0 및 `fail` 판정을 보였습니다. 두 시험에서 QA·자동 평가·자동 진화·check-package를 껐으며 실제 모델과 이 작업 관리 CLI를 실행하지 않았습니다. 이 합성 결과는 고정 커밋 전체 또는 실제 모델에서 같은 동작을 보장하지 않습니다. 따라서 조회 명령의 종료 코드 0만으로 작업 성공을 단정하지 말고 반환된 판정과 실제 결과물을 확인하세요. 이 사례가 모든 실패·성공의 종료 코드나 의미 평가 결과를 보장하지는 않습니다.

별도로 고정 커밋 archive의 소스를 우선 불러오는 환경에서, 대역 작업자가 임시 프로젝트에 `hello.txt`를 만들고 로컬 검증을 통과하는 성공 사례를 확인했습니다. 실행과 별도 상태 조회는 각각 종료 0이었고 상태 판정에 `pass`가 있었습니다. 기존 다른 checkout의 가상환경 의존성과 고정 archive의 테스트 대역을 사용했으며 QA·자동 평가·진화는 끈 합성 시험입니다. 이 예제의 인터뷰나 실제 모델 작업을 검증한 결과는 아닙니다.

## 다음 행동

기능과 테스트가 모두 맞으면 자신의 목표로 같은 순서를 적용합니다. 작업이 아직 진행 중이면 [같은 ID를 계속 조회](/docs/progress-detail/)하고, 실행·검증이 실패했으면 [복구 안내](/docs/recovery-detail/)에서 해당 단계의 절차를 따릅니다. Seed가 목표를 놓쳤다면 실행 전에 필요한 내용을 기존 YAML에 직접 수정하거나 호스트에 수정하도록 요청하고 다시 확인합니다. 인터뷰 수정이 필요하면 요구를 명확히 하되 기존 Seed를 다시 생성해 온톨로지를 덮어쓰지 않습니다.
